## 이 문서를 왜 만들었나

우리 프로젝트 주제가 **"환각을 방지하는 RAG 기반 LLM 질의응답 시스템"**이다. `query_sales`는
자연어 질문을 SQL로 바꿔 판매(sales) DB를 조회해주는 도구인데, "SQL을 잘 만드는 것"보다
**"틀린 답을 그럴듯하게 만들어내지 않는 것"**이 이 프로젝트에서 더 중요한 목표다. 이 문서는
그걸 어떻게 보장할지에 대한 설명이다.

## 1. 왜 이 방식을 선택했는가

### 1.1 조사한 7가지 Text2SQL 방법

Text2SQL(자연어 질문을 SQL로 바꾸는 것)을 구현하는 방법을 조사해보니 크게 7가지가 있었다.

| # | 방법 | 한 줄 설명 |
|---|---|---|
| 1 | **시맨틱 레이어**(Semantic/Metrics Layer) | "매출이 뭐다"처럼 업무 용어의 뜻을 미리 코드/DB에 못박아두는 방식 |
| 2 | **멀티에이전트 + 실행 피드백 자기수정** | SQL을 만들고 실제로 검증해봐서, 틀리면 에러 메시지를 보고 스스로 고치게 하는 방식 |
| 3 | 지식그래프/온톨로지 기반 스키마 링킹 | 테이블이 수백~수천 개일 때, 질문과 관련 있는 테이블만 그래프로 찾아주는 방식 |
| 4 | 특화 파인튜닝 SQL 모델 | SQL 생성만 전문으로 하도록 모델을 따로 학습시키는 방식 |
| 5 | RAG 기반 에이전틱 리트리벌 | "질문 → 검증된 SQL" 예시들을 미리 저장해두고, 비슷한 질문이 오면 그 예시를 찾아 참고시키는 방식 |
| 6 | MCP 기반 표준 인터페이스 | LLM이 DB·문서 같은 외부 도구를 표준화된 방식으로 부르게 하는 프로토콜 |
| 7 | 에이전틱 탐색형 | LLM이 `SHOW TABLES`, `DESCRIBE` 같은 명령을 스스로 반복 실행하며 스키마를 알아내는 방식 |

### 1.2 우리는 1번 + 2번을 골랐다

먼저 탈락하는 것부터 보면 이해가 빠르다.

- **3, 5, 7번은 전부 "스키마가 너무 커서 프롬프트에 다 못 넣는다"는 문제를 푸는 기법이다.**
  우리 sales DB는 테이블 14개, 컬럼 약 220개뿐이라 스키마 전체를 프롬프트에 그냥 다 넣어도
  부담이 없다. 이 기법들이 해결하려는 문제 자체가 우리한테는 없다. 특히 7번은 LLM이
  스키마를 알아내려고 DB에 여러 번 왔다갔다 하는 방식이라, 이미 스키마를 정확히 알고 있는
  우리 입장에서는 시간과 비용만 더 든다.
- **4번(파인튜닝)**은 학습 데이터·GPU·시간이 많이 필요해서 부트캠프 기간에는 불가능하다.
- **6번(MCP)**은 애초에 "선택지"가 아니다. 프로젝트 필수 기술로 이미 정해져 있고, 1~5·7번
  중 무엇을 고르든 어차피 MCP 위에서 구현하게 된다.

**남는 건 1번과 2번인데, 이 둘은 서로 다른 종류의 실수를 잡아낸다.**

```
실패 유형 A: SQL이 에러가 남         → "없는 컬럼입니다" 같은 에러가 뜸 → 눈에 보임
실패 유형 B: SQL은 멀쩡히 실행되는데 답이 틀림 → 그럴듯한 숫자가 나옴 → 아무도 모름
```

- **1번(시맨틱 레이어)**이 실패 유형 B를 막는다. 예를 들어 "매출"을 계산할 때 취소된
  주문을 넣을지 뺄지를 LLM이 그때그때 판단하게 두면, 같은 질문에 다른 답이 나올 수 있다.
  이걸 아예 DB 뷰에 "취소·초안은 항상 뺀다"고 못박아두면, LLM이 SQL을 어떻게 쓰든 결과가
  항상 같은 규칙을 따르게 된다.
- **2번(실행 피드백 자기수정)**이 실패 유형 A를 막는다. LLM이 만든 SQL을 실제로 실행하기
  전에 MySQL에게 "이거 실행할 수 있어?"만 미리 물어보고(`EXPLAIN`), 안 되면 그 에러
  메시지를 LLM에게 다시 보여줘서 스스로 고치게 한다.

실패 유형 B가 더 위험하다. 에러 없이 그럴듯한 숫자가 나오기 때문에 아무도 틀렸다는 걸
눈치채지 못한다. 그래서 1번(정의를 못박는 것)이 이번 설계의 중심이고, 2번은 그걸 보완하는
역할이다.

> 참고: 아래 12절에 "이 방식의 한계"를 별도로 정리해뒀다. 2번은 실패 유형 A만 잡을 뿐,
> 여전히 못 잡는 실패 유형 B가 남아있다.

## 3. 뷰(VIEW) 테이블을 만드는 이유

### 왜 원본 테이블을 그냥 안 쓰나

식당 비유로 설명하면: 요리사마다 "곱빼기"의 양을 다르게 생각하면 손님이 매번 다른 양을
받는다. "곱빼기 = 면 200g"이라고 규칙을 정해두면 누가 만들어도 똑같다.

**뷰가 그 규칙을 못박아두는 창구다.** "매출 = 취소·초안 뺀 주문 금액 합"이라는 정의를
뷰 안에 넣어두면, LLM이 SQL을 어떻게 쓰든 그 규칙을 어길 수가 없다. LLM에게 "이 규칙
지켜주세요"라고 프롬프트로 부탁하는 게 아니라, **애초에 어길 방법이 없게 만드는 것**이다.

### 3중 방어 구조

```
1층  MySQL 뷰       취소 제외, 개인정보 제외, 헤더-상세 뻥튀기(fan-out) 방지를 DB가 강제
2층  DB 권한         조회 계정은 뷰만 볼 수 있고 원본 테이블은 아예 못 봄
3층  SQL 검사        실행 전 문법·안전성 검사 + EXPLAIN 사전 채점
```

만들 뷰 5개:

| 뷰 | 담는 내용 | 용도 |
|---|---|---|
| `v_sales_order` | 유효한 주문(취소·초안 제외) | 매출, 고객별·기간별 집계 |
| `v_sales_order_line` | 유효한 주문의 상세 항목 (헤더 금액은 일부러 안 넣음) | 품목별·수량 집계 |
| `v_invoice` | 청구서 | 청구액, 미수금, 연체 |
| `v_customer` | 고객 정보 (개인정보 칸은 뺌) | 고객 목록·속성 |
| `v_sales_order_status` | 상태별·월별 집계 (취소 포함) | "취소된 주문 몇 건?" 같은 질문 |

특히 `v_sales_order_line`에서 주문 헤더 금액을 일부러 뺀 이유: 주문 1건에 상세 항목이
평균 2.7개 딸려 있는데, 헤더 금액과 상세를 그냥 JOIN해서 더하면 상세 개수만큼 금액이
중복으로 더해진다("뻥튀기", fan-out). 아예 헤더 금액 칼럼을 뷰에 넣지 않으면 이런 실수
자체가 불가능해진다.

전체 DDL은 [SPEC.md 4.3절](../../SPEC.md#43-뷰-만드는-sql) 참고.

## 4. `.env`에 MySQL 계정을 새로 추가하는 이유

지금 `.env`에는 쓰기 계정(`MYSQL_WRITE_*`, ETL 전용)만 있고, **읽기 전용 계정이 없다.**
그래서 지금 상태로는 `query_sales`의 실제 DB 조회 자체가 불가능하다.

새로 만들 계정 `chatbot_reader`는:

- **SELECT만 가능**하고, 그마저도 **원본 테이블이 아니라 뷰 5개에만** 권한을 준다
- ETL 쓰기 계정(`etl_writer`)과 완전히 분리되어 있어, 챗봇이 실수로 데이터를 고치거나
  지우는 사고가 구조적으로 불가능하다
- README의 핵심 원칙("Read/write separation: Data MCP는 읽기 전용 연결, ETL은 적재 전용
  연결")과 그대로 일치한다

즉 "계정을 하나 늘리는 번거로운 일"이 아니라, **3중 방어의 2층(DB 권한)을 실제로 동작하게
만드는 필수 작업**이다. `.env`에 아래 항목을 추가해야 하며, 이건 통합 담당과 협의가
필요하다 (11절 참고).

```env
MYSQL_READ_HOST=localhost
MYSQL_READ_USER=chatbot_reader
MYSQL_READ_PASSWORD=
SALES_DB_DATABASE=sales
```

## 5. 처리 순서

**`[코드]`는 우리가 짜는 Python 코드, `[LLM]`은 OpenAI 모델 호출, `[MySQL]`은 실제 DB
서버가 처리하는 부분이다.** 이 셋을 구분해서 보면 "LLM이 관여하는 부분이 생각보다
훨씬 적다"는 게 보인다.

```
질문
 │
 ├─(1) 입력 확인 [코드]                빈 질문 / 500자 초과 → 거절
 │
 ├─(2) 범위 확인 [코드]                판매 범위 밖 → 거절 (권한 안내)
 │                                    뷰로 못 답하는 내용 → 거절 (되묻기)
 │                                    기간이 애매함 → 거절 (되묻기)
 │
 ├─(3) 프롬프트 재료 조립 [코드]        뷰 구조 + 지표 정의 + 오늘 날짜를 준비
 │
 ├─(4) SQL 작성 [LLM] ★               질문 + (3)의 재료 → SQL 문자열 1개
 │
 ├─(5) 1차 검사 [코드]                 SELECT 하나뿐인지 / 위험한 명령어 없는지 / 허용된 뷰만 쓰는지 / LIMIT 붙었는지
 │        │ 위반
 │        └─────────────┐
 ├─(6) EXPLAIN 채점 [MySQL]│  실패
 │        │              │    │
 │        │              ▼    ▼
 │        │        (6a) 재작성 [LLM] ★    실패 이유를 그대로 보여주고 SQL 다시 요청 (최대 1회)
 │        │              │
 │        │              └─→ 재검증도 실패 → QUERY_ERROR로 종료 [코드]
 │        ▼ 통과
 ├─(7) 실제 조회 실행 [MySQL]           조회 전용 계정(`chatbot_reader`), 최대 10초
 │
 ├─(8) 결과 정리 [코드]                0건이면 "없다"고 안내 / LLM용 50행 · 화면용 전체로 나눔
 │
 └─(9) 결과 반환 [코드]                query_sales()의 최종 반환값 조립 → 다음 단계(답변 생성)로 전달
```

**LLM은 (4)와 (6a), 딱 두 곳에서만 불린다.** 나머지 7단계는 전부 우리 Python 코드나
MySQL이 처리한다. "정의를 코드에 못박아서 LLM이 판단할 기회 자체를 줄인다"는 시맨틱
레이어의 목표(1절)가 실제로는 이렇게 구현된다 — LLM 관여 지점을 최소화하는 것.

## 6. 각 처리 순서별 세부 내용 — 누가, 무엇을 받아서, 무엇을 반환하나

| 단계 | 담당 | 무엇을 받나(입력) | 무엇을 반환하나(출력) | 왜 이렇게 하나 |
|---|---|---|---|---|
| (1) 입력 확인 | **코드** (`query.py`) | 사용자 질문 문자열 | 통과 → 다음 단계 / 실패 → `error_code="INVALID_INPUT"` 즉시 반환하고 종료 | 의미 없는 질문에 LLM 호출을 낭비하지 않기 위해 |
| (2) 범위 확인 | **코드** (`query.py` + `schema.py`의 `out_of_scope` 목록) | 질문 문자열 | 통과 → 다음 단계 / 실패 → `INVALID_INPUT` 반환하고 종료 | SQL을 만들기 전에 걸러야 "그럴듯한 오답" 자체가 안 생김 |
| (3) 재료 조립 | **코드** (`schema.py`) | (질문은 안 씀. 뷰 구조·지표 정의는 코드에 이미 고정돼 있고, 오늘 날짜만 그 순간 새로 계산) | `SchemaResource` — 뷰 목록·지표 정의·오늘 날짜·데이터 보유 기간을 담은 딕셔너리 | LLM이 스스로 판단할 여지를 최대한 줄이기 위해 |
| (4) SQL 생성 | **LLM** | 질문 + (3)에서 만든 `SchemaResource` | SQL 문자열 1개 (아직 검증 전) | 자연어 → SQL 변환은 LLM만 할 수 있는 부분 |
| (5) 1차 검사 | **코드** (`sql_guard.py`) | (4)의 SQL 문자열 | 통과 → 검사·보정된 SQL을 다음 단계로 / 실패 → (6a)로 이동 | LLM이 실수해도 위험한 SQL이 실행 전에 코드로 걸러짐 |
| (6) EXPLAIN 채점 | **MySQL** (코드가 요청만 보냄) | 검사를 통과한 SQL | 통과 → "실행 가능" 응답 / 실패 → MySQL이 뱉은 에러 메시지 | 실제 데이터는 안 건드리고 "이 SQL 돌아가?"만 미리 확인 |
| (6a) 재작성 | **LLM** | 실패했던 SQL + MySQL 에러 메시지 | 새 SQL 문자열 1개 (딱 1번만 시도) | 사람이 지적하는 것보다 실제 에러 메시지가 더 정확한 힌트가 됨 |
| (7) 실제 실행 | **MySQL** (`chatbot_reader` 계정) | 최종 통과된 SQL | 조회 결과 행들 (또는 실행 오류) | 조회 전용 계정이라 실수로 데이터를 고치거나 지울 수 없음 |
| (8) 결과 정리 | **코드** (`query.py`) | (7)의 원본 조회 결과 | 화면용 `rows`(전체) / LLM용 `rows_for_llm`(최대 50행) / `row_count`, `truncated` 등 | 화면에는 다 보여주고, LLM 프롬프트는 너무 길어지지 않게 |
| (9) 반환 | **코드** (`query.py`) | (8)에서 정리한 결과 | `query_sales()`의 최종 반환값(딕셔너리) → `app/agent/nodes.py`로 전달 | 여기까지가 `query_sales`의 책임. 자연어 답변 문장을 쓰는 건 이 함수 바깥 |

> **참고**: 사람이 읽을 답변 문장을 실제로 쓰는 LLM 호출은 `query_sales` 바깥에서
> 한 번 더 일어난다 (`app/agent/nodes.py`의 `answer_synthesis`, 통합팀 소유 —
> [SPEC.md 8.3절](../../SPEC.md) 참고). 즉 질문 하나당 LLM은 보통 SQL 생성 1회
> (+ 실패 시 재작성 1회) + 답변 생성 1회, 최대 3번까지 불릴 수 있다.

## 8. 답변 불가능한 SQL 시나리오

### 8.1 sales 팀 이외의 계정/질문이 sales 정보를 물을 때

두 가지 경우가 있는데, 이중으로 막혀 있다.

1. **다른 도메인 질문이 우리 도구로 잘못 들어온 경우** (예: "공급업체 발주 현황"이 실수로
   `query_sales`로 라우팅됨) → `query_sales`가 자기 자신도 한 번 더 "이거 내 담당 맞아?"를
   확인해서, 판매 범위 밖이면 "판매 데이터 조회 권한 범위를 벗어난 질문입니다"로 거절한다.
2. **다른 도메인의 조회 도구가 sales 데이터에 접근하려는 경우** — 이건 애초에 코드 로직과
   무관하게 **DB 권한(3절 2층)에서 막힌다.** `chatbot_reader`(sales 전용 계정)에게는
   sales 뷰 5개에만 권한이 있고, purchase 쪽 계정에는 sales 뷰 권한 자체가 없다. 즉
   라우팅 로직에 버그가 있어도 DB가 마지막 방어선 역할을 한다.

### 8.2 고객(customer) 정보를 물어볼 때

- 이메일, 전화번호, 청구/배송 주소, 세금번호, 담당자 이름 같은 **개인정보(PII) 칼럼은
  아예 뷰(`v_customer`)에 넣지 않는다.** LLM에게 주는 스키마 정보에도 이 칼럼들의 존재
  자체가 안 나간다.
- 그래서 "고객 이메일 알려줘" 같은 질문은 애초에 조회할 데이터가 없어서 **자연스럽게
  거절**된다. "그 정보는 판매 데이터 조회 범위에 포함되지 않습니다"로 답한다.
- 고객명·업종·국가·거래유형처럼 개인정보가 아닌 항목은 정상적으로 조회 가능하다.
- 혹시라도 나중에 실수로 PII 칼럼이 뷰에 들어가는 경우를 대비해, 결과에 개인정보가 섞여
  있으면 이용 목적 제한 안내 문구를 붙이는 안전장치도 코드에 남겨둔다(현재는 발생할 일이
  거의 없는 최후 방어선).

### 8.3 그 밖에 답할 수 없는 시나리오

| 시나리오 | 예시 | 왜 안 되나 |
|---|---|---|
| 원가·이익 관련 | "이번 달 영업이익 얼마야" | 원가 데이터 자체가 없음. "매출 기준으로는 안내 가능"이라고 대안 제시 |
| 재고·구매 관련 | "재고 얼마나 남았어", "발주 현황" | sales DB에 없는 정보(재고는 애초에 테이블이 없고, 구매는 다른 팀 도메인) |
| 뷰 밖 테이블 | "이번 분기 견적 목록", "배송 현황" | 견적·배송·여신한도·할인정책·매출예측은 이번 범위에서 뷰로 만들지 않음 |
| 기간이 불명확 | "최근 매출 어때?" | "최근"이 언제인지 되물음 |
| 고객명 오타/부분일치 | "삼성 매출" | 고객 목록에 정확히 일치하는 이름이 없으면 다시 확인 요청 |
| 상식으로 추론해야 하는 질문 | "제약회사들 매출 합계" | 가짜 데이터라 실제 제약회사도 업종이 다르게 적혀있는 경우가 있어, LLM이 상식으로 짐작하면 틀림 → 상식 추론 자체를 금지 |
| 해당 기간 데이터가 실제로 없음 | "이번 달 매출"(오늘 기준) | 가장 최근 주문이 2026-06-23이라 "이번 달"은 구조적으로 항상 0건. 에러가 아니라 "없다"고 정직하게 답함 |

**다른 팀과 함께 풀어야 하는 문제**(`.env` 계정 추가, `nodes.py` import 오류, 화면
표시 관련 이슈 등)는 별도로 **[팀 공유 자료 3] 다른 팀에게 요청할 개발 내용**에서
정리한다.

## 12. 이 방식의 문제점

1번(시맨틱 레이어)+2번(실행 피드백 자기수정) 조합도 완벽하지 않다. 미리 알아둬야 할
한계를 정리한다.

- **실행 피드백은 "에러가 나는 SQL"만 잡는다.** `SELECT SUM(total_amount) FROM
  sales_orders`처럼 취소 주문까지 포함해서 계산하는 SQL은 문법도 맞고 실행도 잘 되기
  때문에 EXPLAIN도 통과한다. 이런 "의미는 틀렸지만 에러는 안 나는" 실수는 2번(실행
  피드백)이 못 잡고, 오직 1번(뷰로 아예 취소를 빼버리는 것)이 막는다. 즉 뷰로 미리
  막아두지 않은 부분은 여전히 취약하다.
- **뷰를 늘릴 때마다 사람이 직접 DDL을 작성해야 한다.** 새로운 지표나 질문 유형이
  생기면 자동으로 대응되는 게 아니라, 개발자가 매번 뷰를 새로 설계하거나 고쳐야 한다.
  유연성이 낮다.
- **뷰 밖의 질문에는 아예 답을 못 한다.** 견적·배송·여신한도처럼 이번에 뷰로 안 만든
  영역은 데이터가 DB에 있어도 조회가 불가능하다(의도된 제약이지만, "왜 이건 안 되냐"는
  질문을 받을 수 있음).
- **작은 데이터셋에서 검증된 설계라, 데이터가 훨씬 커지면 다시 봐야 한다.** 지금은 제일
  큰 테이블이 200행이 안 돼서 `LIMIT 200`이 사실상 "전체 반환"과 같다. 데이터가 수만~
  수십만 행으로 늘어나면 응답 속도·비용·요약 방식을 다시 설계해야 한다.
- **EXPLAIN은 "실행 가능한가"만 검증하지, "질문에 대한 올바른 답인가"는 검증하지
  못한다.** 컬럼명 오타나 문법 오류는 잡지만, "질문의 의도를 잘못 이해해서 엉뚱한 뷰를
  골랐다" 같은 실수는 EXPLAIN을 통과한다.

## 13. 현업에서 많이 쓰이는 Text2SQL

> 아래는 특정 논문이나 벤치마크를 확인하고 쓴 게 아니라, 일반적으로 알려진 업계 경향을
> 참고용으로 정리한 것이다. 정확한 최신 사례가 필요하면 별도로 조사가 필요하다.

실무에서는 한 가지 기법만 단독으로 쓰기보다, 데이터 규모와 목적에 따라 여러 기법을
조합하는 경우가 많다고 알려져 있다.

- **시맨틱/메트릭 레이어**는 회사의 핵심 지표(매출, 이익 등)를 다루는 곳에서 가장
  기본으로 깔고 가는 경향이 있다. "지표 정의가 팀마다 다르면 안 된다"는 요구가 강한
  환경(재무, 경영 보고 등)일수록 중요하게 다뤄진다.
- **스키마 링킹/예시 검색(RAG)**은 테이블이 수백~수천 개인 대규모 데이터 웨어하우스에서
  필수에 가깝다. 스키마를 전부 프롬프트에 넣을 수 없기 때문이다. 우리 프로젝트처럼
  테이블이 10~20개 수준이면 상대적으로 덜 중요하다.
- **실행 피드백 자기수정**은 구현 난이도에 비해 정확도가 크게 오르는 편이라, 규모와
  무관하게 거의 기본으로 들어가는 경향이 있다.
- **멀티에이전트(역할 분리)**는 복잡한 분석 질문을 다루는 고급 시스템에서 쓰이지만,
  LLM 호출이 늘어나 응답 속도·비용 부담이 커서 정말 필요한 경우에만 선택적으로
  쓰이는 편이다.
- **특화 파인튜닝 모델**은 자체 데이터·인프라가 충분한 대기업에서 주로 쓰이고, 작은
  팀·프로젝트에서는 잘 안 쓰인다.

우리가 고른 "1(정의 고정) + 2(실행 피드백)" 조합은, 업계에서도 가장 기본으로 깔고
시작하는 조합과 방향이 같다. 3·5·7번(스키마 링킹류)을 뺀 이유도 "우리 규모에서는
아직 필요 없다"는 것이지 "나쁜 방법이라서"가 아니다. 나중에 뷰·테이블이 훨씬 많아지면
다시 검토할 수 있다.
