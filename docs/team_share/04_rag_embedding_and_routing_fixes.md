## 1. `min_relevance` 임계값 완화

**파일**: `app/agent/state.py`

```python
min_relevance: float = 0.5   # 기존
min_relevance: float = 0.2   # 수정 후 (로컬 임베딩 기준)
```

**원인**: 이 값은 "근거로 인정할 최소 관련성 점수"인데, 원래 OpenAI 임베딩(코사인 유사도
0.7~0.9대)을 기준으로 정해진 값으로 보임. 그런데 실제로는 로컬(n-gram) 임베딩을 쓰고
있었고, 이 방식은 점수대가 훨씬 낮게(0.1~0.4) 나옴. 그래서 실제로는 관련 있는 문서를
찾아놓고도 "관련성 기준 미달"로 다 걸러지고 있었음.

**참고**: 이번에 sentence-transformers로 다시 바꾸면서 점수대가 또 달라짐(관련 있음
0.67 vs 관련 없음 0.22 확인됨). 이 값은 **다시 한번 조정이 필요**하며, 현재 `0.4` 전후로
재설정 검토 중.

## 2. DCC-008 — 임시 인덱스 → 정식 인덱스 재사용

**파일**: `mcp_servers/document_tools/rag.py`

**원인**: 기존 `retrieve()`는 질문이 들어올 때마다:
1. 문서 DB에서 관련 문서 경로를 조회
2. 그 문서들을 파일에서 다시 읽고
3. 다시 청킹하고
4. **다시 임베딩해서**
5. 임시 FAISS 인덱스를 만들고
6. 검색 끝나면 그 인덱스를 바로 삭제

이 구조는 두 가지 문제가 있었음:
- **질문마다 임베딩을 반복 계산** — 로컬 임베딩일 땐 공짜라 안 드러났지만,
  sentence-transformers/OpenAI로 바꾸면 질문 하나에 문서 10개어치를 매번
  다시 임베딩하게 되어 느려지고(또는 비용 발생) 비효율적임
- **`index_version`을 추적할 방법이 없음** — 인덱스가 매번 새로 만들어지고
  버려지니, "지금 쓰는 인덱스가 몇 번째 버전인지"를 캐시 무효화 등에 쓸 수 없었음

**수정**: `scripts/ingest_documents.py`가 미리 만들어둔 정식 인덱스(`data/faiss/`)를
그대로 로드해서 검색하도록 변경. 문서 DB 조회 결과(`document_id` 목록)는 이제
"인덱스를 새로 만들 재료"가 아니라 "검색 결과를 좁히는 필터"로 역할이 바뀜.

```python
# 이전: 질문마다 임시 인덱스 생성
tmp_dir = tempfile.mkdtemp(...)
build_index(chunks, vectors, tmp_dir)  # 매번 재임베딩
...
shutil.rmtree(tmp_dir)  # 바로 삭제

# 이후: 정식 인덱스를 프로세스 안에서 재사용, 결과만 document_id로 필터링
store, index_version = _load_persistent_store()  # 캐시된 인덱스 재사용
candidates = store.search(query_vector, top_k * 5)
results = [c for c in candidates if c["document_id"] in allowed_document_ids][:top_k]
```

**추가로 같이 고친 것** (DCC-008 감사 항목에 같이 적혀 있던 내용):
- `mcp_servers/document_tools/types.py`의 `DocumentChunk`에 `page` 필드 추가
- `faiss_store.py`가 검색 결과에 `page` 값을 채워서 반환
- `document_id`, `page`, `index_version`이 실제 API 응답(`sources`)까지 흘러가도록 연결

**⚠️ 중요 — 구조적으로 중복돼 있던 부분도 같이 고침**: `mcp_servers/document_tools/server.py`
(MCP 정식 등록 도구)와 `app/mcp/client.py`의 `InProcessMCPPort`에 **완전히 동일한 응답
조립 로직이 두 군데 따로 있었음.** 실제 채팅 흐름은 `InProcessMCPPort` 쪽만 타기 때문에,
`server.py`만 고치면 반영이 안 되는 상태였음. **앞으로 `search_documents` 응답 형식을
바꿀 일이 있으면 두 파일 다 확인해야 함.**

## 3. 라우팅 키워드/정규화 버그

**파일**: `app/agent/nodes.py`

### 3-1. 키워드 부족
```python
# 이전
document_terms = ("정책", "규정", "가이드", "매뉴얼", "문서", "지침", "절차", "휴가", "휴직", "취업규칙")

# 이후 — 실제 등록된 사내규정 10종의 제목에서 뽑은 단어 추가
document_terms = (
    "정책", "규정", "가이드", "매뉴얼", "문서", "지침", "절차", "휴가", "휴직", "취업규칙",
    "법인카드", "카드", "계약", "복지", "후생", "안전보건", "인사", "직원보수", "보수", "급여", "회계",
)
```
**원인**: "법인카드 규정 알려줘" 같은 질문에 위 목록 단어가 하나도 없으면 `GENERAL`(일반
대화)로 분류돼서 문서 검색 자체를 시도하지 않았음. 데이터가 없어서가 아니라 애초에
검색을 안 한 것.

### 3-2. 띄어쓰기 민감
```python
# 이전
normalized = question.casefold()

# 이후
normalized = "".join(question.casefold().split())
```
**원인**: "취업 규칙"(띄어쓰기 있음)으로 물어보면 "취업규칙"(붙어있음) 키워드와 매칭이
안 돼서 역시 `GENERAL`로 빠짐. 청킹/임베딩 쪽은 이미 공백을 무시하도록 되어 있었는데
라우팅 쪽만 놓쳐서 생긴 불일치.

## 4. 임베딩 백엔드 전환: local → sbert (sentence-transformers)

**파일**: `ingestion/embedding.py`, `app/core/config.py`, `.env`

### 원인 — 로컬(n-gram) 임베딩의 근본적 한계
로컬 임베딩은 "글자가 겹치는가"만 보는 방식(문자 2-gram/3-gram을 해싱)이라:
- "규정"과 "지침"처럼 의미는 같아도 글자가 다르면 전혀 무관한 것으로 취급됨
- 질문이 짧고 문서 조각(청크)이 길면, 정확히 일치하는 단어가 있어도 코사인 유사도가
  구조적으로 낮게 나옴 (겹치는 부분보다 안 겹치는 부분이 압도적으로 많아서)
- 해시 충돌로 **무관한 조각이 우연히 높은 점수를 받는 경우**도 실제로 확인됨
  (예: "취업규칙"으로 검색했는데 "개정이력" 메모가 1등으로 나옴)

실측 비교(같은 질문·같은 문서 기준):

| | 로컬(n-gram) | sentence-transformers |
|---|---|---|
| "취업규칙" 정확히 일치하는 문서 점수 | 0.08 ~ 0.12 | - |
| 관련 있는 문장 간 유사도 | - | 0.672 |
| 무관한 문장 간 유사도 | - | 0.221 |

→ 로컬 방식은 정답과 오답의 점수 차이가 거의 없어서 임계값을 어떻게 잡아도 불안정했고,
sentence-transformers는 차이가 뚜렷해서(0.45) 안정적으로 기준을 잡을 수 있음.

### 수정 내용
`ingestion/embedding.py`의 `EmbeddingClient`가 `local` / `sbert` / `openai` 세 백엔드를
지원하도록 확장. 전환은 `.env` 한 줄로 가능:
```
EMBEDDING_BACKEND=sbert
```
사용 모델: `jhgan/ko-sroberta-multitask` (한국어 튜닝, 최초 1회 다운로드 후 오프라인
동작, API 비용 없음).

### 실측 성능 (실제 팀원 PC에서 측정)
- 모델 로딩: 19초 (서버 시작 시 1회만)
- 임베딩 속도: 텍스트 1개당 30ms
- 문서 10개(청크 ~380개) 재인덱싱: 약 10초

### ⚠️ 전환 시 팀원들이 해야 할 일
1. `.env`에 `EMBEDDING_BACKEND=sbert` 추가
2. `pip install sentence-transformers` (아직 없다면)
3. **재인덱싱 필수**: 기존 로컬 임베딩 인덱스는 차원이 달라서(384 vs 768) 호환 안 됨
   ```
   python scripts/ingest_documents.py
   ```
4. `min_relevance` 값은 로컬 기준(0.2)으로 맞춰져 있어서, sbert 기준으로 **재조정 필요**
   (현재 0.4 전후로 검토 중, 확정되면 별도 공유 예정)
