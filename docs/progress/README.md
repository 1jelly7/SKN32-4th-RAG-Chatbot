# 진행 이력 운영 가이드

`docs/progress/`는 팀의 작업 인수인계를 위한 날짜별 진행 이력(progress log)이다. 단순 업무 일지가 아니라 실제 변경 사항, 검증 결과, 의사결정과 트레이드오프, 차단 요인, 다음 시작점을 보존한다.

`PROGRESS.md`는 **현재 검증 상태와 최우선 다음 작업을 보는 요약본**이고, `docs/progress/<role>/YYYY-MM-DD.md`는 **영역·날짜별 상세 이력**이다. `PROGRESS.md`에 과거 이력을 복사하지 말고 관련 일별 파일을 링크한다.

## 공식 구조

```text
docs/
  progress/
    README.md
    backend/
      2026-08-02.md
      2026-08-03.md
    rag/
      2026-08-02.md
      2026-08-03.md
    sales/
      2026-08-02.md
      2026-08-03.md
    purchase/
      2026-08-02.md
      2026-08-03.md
    integration/
      2026-08-02.md
      2026-08-03.md
```

실제 작업이 없었던 날짜에는 파일을 만들지 않는다. 기본 깊이는 반드시 `docs/progress/<role>/YYYY-MM-DD.md`이며, 불필요하게 하위 디렉터리를 늘리지 않는다. 각 역할 폴더는 필요하면 자체 `README.md`로 용어, 지표, 외부 시스템 링크를 안내할 수 있다.

## 책임 영역

| 역할 | 책임 범위 | 기록 대상 예시 |
| --- | --- | --- |
| `backend` | API, 인증·권한, 데이터베이스, 비즈니스 로직, 비동기 작업, 백엔드 배포·운영 설정 | API/DB 마이그레이션, 인증 API 수정, 서비스 로직·운영 설정 |
| `rag` | 데이터 수집·정제·청킹·임베딩·검색·리랭킹, RAG 평가, 정확도·비용·지연시간 실험 | 벡터 DB 재색인, retriever/reranker 평가, 평가 데이터셋·지표 |
| `sales` | 고객 발굴, 영업 파이프라인, 고객 요구사항, 제안·데모, 가격·성과 | 고객 요구사항 수집, 데모·미팅 결과, 제안서·PoC 범위 |
| `purchase` | 공급업체 조사·선정, 견적·발주, 구매 승인, 계약·결제, 조달·납기 리스크 | LLM API 공급업체 견적 비교, 발주/계약 검토, 납기·리스크 |
| `integration` | 두 영역 이상을 건드리는 변경, API 연동, E2E, 스테이징·프로덕션 배포, 릴리스, 공통 관측성·보안 | RAG 결과 FastAPI 반환, 권한 필터 E2E, 릴리스·공통 보안 |

폴더는 개인 소유가 아니라 **변경 책임과 도메인 경계**로 나눈다. 개인별 일지나 역할 밖의 사소한 작업을 별도 폴더로 만들지 않는다.

## 기록 위치 결정

- 한 영역에만 영향을 주는 작업은 해당 역할의 날짜 파일에 기록한다.
- 둘 이상의 영역, API 계약, E2E, 릴리스·보안·공통 관측성처럼 팀 전체에 영향을 주는 작업은 `integration/YYYY-MM-DD.md`에 정본(canonical record)을 기록한다.
- 교차 영역 작업의 개별 역할 파일에는 짧은 요약과 정본 링크만 남긴다. 동일 내용을 여러 파일에 복제하지 않는다.

예시:

- RAG 검색 결과를 반환하는 FastAPI 응답 구현 → `integration/`
- 벡터 DB 재색인과 리랭커 오프라인 평가 → `rag/`
- 고객별 검색 권한 필터를 API와 retriever에 함께 적용 → `integration/`
- 고객 요구사항 수집과 데모 결과 → `sales/`
- LLM API 공급업체 계약·발주·납기 리스크 → `purchase/`
- DB 마이그레이션과 인증 API 수정 → `backend/`

## 일별 파일과 세션 규칙

진행 이력은 **일별 파일로만** 기록한다.

- 파일명은 `YYYY-MM-DD.md` 형식만 사용한다. 월별·주별·역할별 누적 파일은 만들지 않는다.
- 날짜는 실제 작업을 수행한 시점의 KST(`Asia/Seoul`)를 기준으로 한다.
- 같은 날짜·역할의 여러 작업은 시간순으로 한 파일에 세션을 추가한다.
- 세션은 작업의 기본 단위이며, 한 세션은 하나의 작업 흐름이다. 작은 파일 수정, 재실행, 단순 리팩터링은 별도 세션이 아니라 해당 세션의 `Changes`에 묶는다.
- 세션을 시작할 때 목표를 기록하고, 종료할 때 실제 변경·검증 범위·다음 시작점을 갱신한다.
- 세션이 자정을 넘기면 시작한 날짜 파일에 기록한다. 다음 날 별도 목표로 재개하면 다음 날짜 파일에 새 세션을 만들고 이전 파일의 `Next Steps`를 참조한다.
- API/계약 변경, 테스트·CI·배포 상태 변화, 재현 가능한 결론, 외부 의존성 차단, 독립 확인 실험이 생기면 세션 안에 `Checkpoint`를 추가한다.

## 일별 파일 템플릿

코드 변경이 없는 영업·구매 작업도 기록할 수 있도록 `Files Changed / Artifacts`를 사용한다. 민감한 원문은 기록하지 않고 식별자나 접근 제어된 참조만 남긴다.

```md
# YYYY-MM-DD 역할 진행 이력

- 역할: `backend | rag | sales | purchase | integration`
- 타임존: `Asia/Seoul (KST)`
- 일일 요약: <그날의 검증된 상태와 가장 중요한 다음 판단>

## Session N — HH:MM–HH:MM KST | 작업 ID · 짧은 제목

- 작성자: <이름 또는 팀 식별자>
- 역할: `<role>`
- 상태: `Done | In progress | Blocked | Rolled back`
- 브랜치: `<branch 또는 N/A>`
- 이슈 / PR / 커밋 / 관련 링크: `<ID, URL, SHA 또는 N/A>`

### Goal
- <완료 판단이 가능한 목표>

### Scope
- 포함: <범위>
- 제외: <의도적으로 하지 않은 범위>

### Changes
- <변경 또는 수행 내용>

### Files Changed / Artifacts
- `<파일 경로 또는 산출물>`: <무엇이 바뀌었거나 무엇을 확인할 수 있는지>

### Verification
- `<명령, 테스트, CI 실행 ID, 검토 또는 측정>`: <결과>

### Not Verified
- <아직 검증하지 못한 항목 또는 `없음`>

### Issues / Blockers
- <차단 요인, 영향, 필요한 지원 또는 `없음`>

### Decisions
- <결정, 근거, 트레이드오프>

### Next Steps
1. <다음 시작 가능한 작업>

### Learnings
- <재사용 가능한 학습 또는 주의사항>
```

`Done`은 증거가 있을 때만 사용한다. 개발 작업은 테스트 결과·코드 검토·CI 실행 ID·배포 검증·모니터링 지표 등을 남긴다. RAG 작업은 데이터셋 버전, 평가 조건, Recall/MRR/nDCG 또는 정확도·완결성·지연시간·비용을 남긴다. Sales는 고객/기회 식별자, 미팅 결과, 합의와 다음 단계, CRM 링크를 남긴다. Purchase는 공급업체와 견적/발주/계약 식별자, 금액·통화·승인·납기·리스크를 남긴다.

고객 정보, API 키, 계약 원문, 개인정보, 비밀번호, 내부 경로는 직접 기록하지 않는다. 접근 권한이 있는 시스템의 식별자 또는 링크만 남긴다. 전체 콘솔 출력, 대용량 실험 결과, 스크린샷, 모델 출력, CI 전문 로그, 계약 원문은 별도 저장소·CI 아티팩트·문서 시스템에 보관하고 여기에는 URL, 실행 ID, 데이터셋 버전, 커밋 SHA 같은 추적 가능한 참조만 기록한다.

## 일별 파일 완성 예시

```md
# 2026-08-02 RAG 진행 이력

- 역할: `rag`
- 타임존: `Asia/Seoul (KST)`
- 일일 요약: 리랭커 후보 2종의 오프라인 평가를 마쳤으며, 최종 모델 선정은 비용 검토 후 결정한다.

## Session 1 — 09:30–12:10 KST | RAG-081 리랭커 후보 평가

- 작성자: rag-team
- 역할: `rag`
- 상태: Done
- 브랜치: `experiment/reranker-eval`
- 이슈 / PR / 커밋 / 관련 링크: RAG-081 / #187 / `a1b2c3d`

### Goal
- 후보 리랭커 A와 B의 검색 품질, 응답 지연시간, 추론 비용을 비교한다.

### Scope
- 포함: 오프라인 평가, 상위 10개 문서 재정렬 성능 측정
- 제외: 온라인 A/B 테스트, 운영 배포

### Changes
- 평가 파이프라인에 후보 B 모델 선택 인자를 추가했다.
- 데이터셋 `rag-eval-v2026-08-01` 기준으로 평가를 실행했다.

### Files Changed / Artifacts
- `scripts/evaluate_reranker.py`: 후보 모델 선택 인자
- `artifacts/eval/reranker-2026-08-02.json`: 원본 평가 결과
- 실행 대시보드: `<URL 또는 실행 ID>`

### Verification
- `python scripts/evaluate_reranker.py --dataset rag-eval-v2026-08-01`: 완료
- 후보 A: nDCG@10 0.71, p95 310ms
- 후보 B: nDCG@10 0.75, p95 470ms

### Not Verified
- 운영 트래픽을 기준으로 한 비용 추정

### Issues / Blockers
- 후보 B는 품질이 높지만 p95 지연시간이 목표를 초과한다.

### Decisions
- 모델 선정은 비용 추정과 캐시 적용 실험 뒤에 확정한다.
- 트레이드오프: 품질 향상 대 응답 지연시간 증가

### Next Steps
1. 후보 B에 캐시를 적용한 뒤 p95 목표 충족 여부를 측정한다.
2. 일일 예상 요청량을 기준으로 비용을 산정한다.

### Learnings
- RAG 평가는 데이터셋 버전과 실행 ID를 함께 남겨야 재현할 수 있다.
```

## 교차 영역 기록 예시

`integration/2026-08-02.md`의 정본:

```md
## Session 2 — 14:00–15:20 KST | INT-042 고객 권한 필터 E2E 적용

- 작성자: platform-team
- 역할: `integration`
- 상태: Done
- 브랜치: `feature/customer-search-scope`
- 이슈 / PR / 커밋 / 관련 링크: INT-042 / #191 / `d4e5f6a`

### Goal
- 고객별 문서 검색 권한 필터가 API와 retriever 경계에서 일관되게 적용됨을 검증한다.

### Scope
- 포함: API 계약, 권한 필터 전달, E2E 계약 테스트
- 제외: 기존 인덱스 재생성

### Changes
- 검색 요청의 고객 범위를 retriever까지 전달하고 권한 없는 문서를 제외했다.

### Files Changed / Artifacts
- `app/...`: 권한 범위 전달 구현
- CI 실행 `#8841`: E2E 결과

### Verification
- `python -m pytest tests/integration`: 통과

### Not Verified
- 스테이징 트래픽 기반 지연시간 확인

### Issues / Blockers
- 없음

### Decisions
- 교차 영역 계약 변경의 정본은 `integration/`에 둔다.

### Next Steps
1. 스테이징 배포 후 검색 지연시간을 확인한다.

### Learnings
- 역할별 파일에는 이 세션의 요약과 정본 링크만 남긴다.
```

관련 `rag/2026-08-02.md`에는 다음처럼 남긴다: `INT-042 권한 필터 연동 지원 완료. 정본: [integration/2026-08-02.md](../integration/2026-08-02.md).`

## PROGRESS.md 갱신

하루의 역할 작업이 끝나거나 의미 있는 세션이 종료될 때 `PROGRESS.md`를 갱신한다. 현재 검증 상태, 영역별 진행 상태, 핵심 차단 요인, 최우선 다음 작업을 최신으로 유지한다. 과거 내용은 복제하지 말고 해당 일별 파일로 링크한다.

상태 표현 예시:

- Backend: 인증 API 통합 테스트 통과, DB 마이그레이션 리뷰 대기
- RAG: reranker 후보 평가 중, 평가 데이터셋 확정 필요
- Sales: 고객 A 데모 완료, PoC 범위 합의 예정
- Purchase: 공급업체 API 견적 비교 중, 보안 검토 대기
- Integration: 권한 필터 E2E 검증 대기

## 운영 원칙

코드·문서·계약·실험 결과와 실제 수행 내용이 달라지는 날에는 그날의 이력을 갱신한다. 위치가 애매하면 먼저 `integration/`에 정본을 기록하고 필요 시 소속 영역을 보조 분류로 남긴다. 과거 일별 기록은 삭제하지 않으며, 잘못된 내용은 현재 사실·원인·조치·결과·참조 위치를 추가해 정정한다.
